What is multi tenancy?

What is it?

Running your software for multiple clients
(aka tenants) at once

Not all Multi-tenancy is equal

What do you think is possible?

Multi-tenancy by infrastructure

  • ✅ App has no knowledge of tenants
  • ✅ Data is perfectly separated
  • ❌ Cross-cutting concerns are harder
  • ❌ High cost of operation
  • ❌ Cross tenant reporting
graph TD RP{{"Reverse Proxy"}} --> A1[App 1] RP --> A2[App 2] RP --> A3[App 3] A1 --> D1[(DB 1)] A2 --> D2[(DB 2)] A3 --> D3[(DB 3)] style RP fill:#00A3E0,stroke:#003865,color:#fff
Each tenant gets their own full infrastructure - servers, databases, everything. Maximum isolation but highest cost.s

Database per tenant

  • ✅ Data is perfectly separated
  • 💭 App needs config per tenant
  • ❌ (still) high cost of operation
  • ❌ Data consistency between tenants
  • ❌ Cross tenant reporting
graph TD APP[Shared Application] --> DBA[(DB Tenant A)] APP --> DBB[(DB Tenant B)] APP --> DBC[(DB Tenant C)]
One application deployment but each tenant gets their own database. Good data separation but still expensive to manage many databases.

Schema per tenant

  • ✅ Data is mostly separate
  • ✅ Lower operation cost
  • ✅ Cross-tenant reporting is possible
  • 💭 App needs config per tenant
  • ❌ Noisy neighbors
graph TD APP[Shared Application] --> DB[(Shared Database)] DB --> SA["Schema A
tenant_a.*"] DB --> SB["Schema B
tenant_b.*"] DB --> SC["Schema C
tenant_c.*"]
Single database with separate schemas per tenant. Good balance of isolation and cost. Cross-tenant reporting becomes possible since data is in the same DB.

Discriminator column

  • ✅ Lower operation cost
  • ✅ Cross-tenant reporting is possible
  • ✅ Easy to set up
  • ✅ Easy to understand
  • 💭 App needs config per tenant
  • ❌ Noisy neighbors
  • ⚠️ Risk leaky tenant data
graph TD APP[Shared Application] --> DB[(Shared Database)] DB --> T["Shared Table"] T --> R1["TenantId=A, Alice, ..."] T --> R2["TenantId=B, Bob, ..."] T --> R3["TenantId=A, Charlie, ..."] T --> R4["TenantId=C, Diana, ..."] style T fill:#fff3e0,stroke:#e67e22
Simplest approach - all data in same tables with a TenantId column. Cheapest to run but highest risk of data leakage if you forget a WHERE clause.

There is no single best approach - it depends on your requirements for isolation, cost, complexity, compliance, and scale.
